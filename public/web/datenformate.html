Asynchronous JavaScript and XML (AJAX):

AJAX ermöglicht es, Daten asynchron vom Server zu laden, ohne die Seite neu zu laden. Dies verbessert die Benutzererfahrung durch dynamische Inhalte. Der Browser kann also Javascript gesteuert kontinuierlich weitere Anfragen an den Server stellen.

Wichtig zum Verständnis: AJAX ist keine eigene Technologie und keine Programmiersprache, sondern ein Konzept – das Zusammenspiel von JavaScript, einer HTTP-Anfrage im Hintergrund, einem Datenformat (heute JSON) und dem DOM. Der Begriff wurde 2005 von Jesse James Garrett geprägt; die zugrundeliegende Technik gab es schon vorher.

Beispiele sind zB die aktualisierenden Suchergebnisse bei der Eingabe in Google Suchleiste.

Der Unterschied zum klassischen Seitenaufruf

Ohne AJAX läuft jede Interaktion über einen vollständigen Request/Response- Zyklus: der Browser schickt die Anfrage, der Server baut die komplette HTML-Seite neu zusammen, der Browser verwirft die alte Seite und rendert alles neu. Dabei gehen Scrollposition, Formularzustand und der Zustand von JavaScript verloren, und das Fenster flackert kurz weiß.

Mit AJAX bleibt die Seite stehen. JavaScript schickt im Hintergrund eine Anfrage, bekommt nur die benötigten Daten zurück (statt einer ganzen Seite) und tauscht gezielt einen Teil des DOM aus. Der Benutzer kann währenddessen weiterarbeiten – daher asynchron: das Skript wartet nicht blockierend auf die Antwort, sondern wird benachrichtigt, sobald sie eintrifft.

Klassischer Seitenaufruf AJAX
Antwort des Servers vollständiges HTML-Dokument nur die Daten (JSON) oder ein HTML-Fragment
Seite wird neu geladen ja, komplett nein, nur ein Teil des DOM wird ersetzt
Übertragene Datenmenge hoch gering
Zustand der Seite geht verloren bleibt erhalten
Benutzer währenddessen wartet, Seite blockiert kann weiterarbeiten

Die Abbildung

Die Abbildung zeigt die beiden Seiten einer AJAX-Kommunikation und das, was dazwischen passiert:

  • Links der Browser – hier läuft die Präsentation. In ihm liegt das JavaScript, das die Anfrage auslöst, die Antwort entgegennimmt und das DOM aktualisiert. Die Beschriftung "Ajax" steht genau für diese Rolle: AJAX ist die Technik auf der Clientseite.
  • Rechts der Webserver und die Datenhaltung – hier liegt die Logik und Persistenz. Der Webserver nimmt die Anfrage entgegen, ein serverseitiges Skript (z.B. PHP) verarbeitet sie, liest oder schreibt in der Datenbank und erzeugt die Antwort.
  • Der rote Doppelpfeil ist der entscheidende Teil: die Kommunikation läuft in beide Richtungen und ausschließlich über HTTP. AJAX erfindet kein eigenes Protokoll – es sind ganz normale HTTP-Requests, nur eben nicht vom Browser-Hauptfenster ausgelöst, sondern von JavaScript.
  • "HTTP, XML, JSON, ..." benennt die Schichten: HTTP ist das Transportprotokoll, XML und JSON sind die Formate, in denen die Nutzdaten darin stecken. Möglich ist auch reiner Text, HTML oder bei Uploads binärer Inhalt.

Die Trennung in der Abbildung ist zugleich die Architekturaussage: Darstellung im Browser, Daten und Logik auf dem Server. Der Doppelpfeil bleibt dabei immer vom Client initiiert – der Server kann von sich aus nichts schicken. Genau dafür gibt es WebSockets und Server-Sent Events.

Das X in AJAX

Das "XML" im Namen ist historisch. Als der Begriff entstand, war XML das übliche Austauschformat. Heute wird praktisch ausschließlich JSON verwendet, weil es kompakter ist und in JavaScript direkt zu einem Objekt wird. Der Name blieb trotzdem – korrekter wäre heute "AJAJ". Auch das "Asynchronous" ist streng genommen nicht zwingend: synchrone Requests wären technisch möglich, blockieren aber den gesamten Browser-Tab und sind deshalb abgeschafft.

Typische Anwendungsfälle

  • Aktualisierende Suchvorschläge während der Eingabe, wie in der Google-Suchleiste (Autocomplete)
  • Formulare absenden, ohne die Seite zu verlassen – inkl. Fehlermeldungen direkt am Feld
  • Nachladen von Inhalten: Infinite Scroll, "Mehr laden", Seitenwechsel in Listen
  • Filter und Sortierung in Produktlisten
  • Live-Validierung, z.B. ob ein Benutzername noch frei ist
  • Warenkorb aktualisieren, Likes, Favoriten, Statuswechsel
  • Datei-Uploads mit Fortschrittsanzeige
  • Single Page Applications – dort ist AJAX nicht Zusatz, sondern der einzige Weg, wie die Anwendung an Daten kommt

Umsetzung: XMLHttpRequest

Gesteuert wurde AJAX ursprünglich über das JavaScript-Objekt XMLHttpRequest (XHR). Es funktioniert bis heute, ist aber umständlich, weil es mit Callbacks und Zustandscodes arbeitet statt mit Promises.

Zuerst folgt die Erzeugung des XMLHttpRequest-Objektes, dann die Methode open aus dieser Klasse und dann die Anzeige des Ergebnisses über JavaScript-Event onreadystatechange. 

const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/produkte.php?kategorie=oefen');

xhr.onload = function () {
  if (xhr.status >= 200 && xhr.status < 300) {
    const daten = JSON.parse(xhr.responseText);
    console.log(daten);
  } else {
    console.error('Fehler:', xhr.status);
  }
};
xhr.onerror = function () {
  console.error('Netzwerkfehler');
};

xhr.send();

Der Zustand wird über readyState (0 bis 4, wobei 4 = fertig) und status (der HTTP-Statuscode) abgefragt. Relevant ist XHR heute noch an zwei Stellen: beim Hochladen mit Fortschrittsanzeige (xhr.upload.onprogress, was fetch nicht kann) und in älterem Code – etwa in jQuery, wo $.ajax(), $.get() und $.post() intern darauf aufsetzen und AJAX über Jahre populär gemacht haben.

Umsetzung: fetch (heutiger Standard)

fetch() ersetzt XHR und arbeitet mit Promises, wodurch sich der Code zusammen mit async/await fast wie synchroner Code liest. 

async function ladeProdukte(kategorie) {
  try {
    const response = await fetch(`/api/produkte.php?kategorie=${encodeURIComponent(kategorie)}`, {
      headers: { 'Accept': 'application/json' }
    });

    // WICHTIG: fetch wirft bei 404 oder 500 keinen Fehler!
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const daten = await response.json();
    render(daten);

  } catch (error) {
    console.error(error);
    zeigeFehlermeldung('Daten konnten nicht geladen werden.');
  }
}

Ein POST mit Formulardaten – der Fall aus dem Formular-Beispiel:

const form = document.getElementById('ajaxForm');

form.addEventListener('submit', async (e) => {
  e.preventDefault();                  // verhindert den normalen Seitenwechsel

  const button = form.querySelector('button');
  button.disabled = true;              // gegen doppeltes Absenden

  try {
    const response = await fetch('/formular-ajax.php', {
      method: 'POST',
      body: new FormData(form)         // Content-Type setzt der Browser selbst
    });

    const ergebnis = await response.json();

    if (ergebnis.status === 'ok') {
      form.reset();
      meldung.textContent = 'Nachricht erfolgreich gesendet.';
    } else {
      meldung.textContent = ergebnis.fehler.join(', ');
    }

  } catch (error) {
    meldung.textContent = 'Verbindung fehlgeschlagen.';
  } finally {
    button.disabled = false;           // läuft in jedem Fall
  }
});

Bei FormData darf der Content-Type nicht selbst gesetzt werden – der Browser ergänzt multipart/form-data inklusive der nötigen boundary. Wird JSON geschickt, muss der Header dagegen explizit gesetzt werden: 

await fetch('/api/speichern.php', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'John', menge: 2 })
});

Die Gegenstelle auf dem Server

Serverseitig ist ein AJAX-Request ein ganz normaler Request. Der Unterschied liegt nur darin, dass kein HTML, sondern JSON zurückgegeben wird – und dass der passende Content-Type gesetzt werden muss. 

<?php
header('Content-Type: application/json; charset=utf-8');

$fehler = [];
$name = trim($_POST['name'] ?? '');

if ($name === '') {
    $fehler[] = 'Name fehlt';
}

if ($fehler) {
    http_response_code(422);                      // Unprocessable Entity
    echo json_encode(['status' => 'error', 'fehler' => $fehler]);
    exit;
}

// ... speichern oder Mail senden ...

echo json_encode(['status' => 'ok']);

Zwei Dinge gehen hier regelmäßig schief:

  • Jede Ausgabe vor json_encode zerstört die Antwort. Ein Leerzeichen vor <?php, eine PHP-Warning oder ein var_dump landen im Response-Body, und response.json() scheitert mit "Unexpected token". Deshalb display_errors produktiv auf Off und Fehler ins Log.
  • Wird ein JSON-Body geschickt (Content-Type: application/json), ist $_POST leer. Dann muss der Rohinhalt gelesen werden: $daten = json_decode(file_get_contents('php://input'), true);

Ein ausführbares Beispiel liegt in diesem Projekt unter backend/formular-ajax.php zusammen mit dem Formular unter "Formular mit AJAX".

Probleme und Fallstricke bei AJAX

Vor und zurück Tasten haben nun eine unlogische Bedeutung. Ebenso kann man nur auf den Startzustand einer AJAX Anwendung verlinken.

Same-Origin-Policy und CORS

Der Browser erlaubt JavaScript standardmäßig nur Anfragen an die gleiche Herkunft (Origin = gleiches Protokoll, gleiche Domain, gleicher Port). http://localhost:8000 und http://localhost:5173 sind damit bereits zwei verschiedene Origins. Soll eine fremde Domain angesprochen werden, muss der Server das per CORS-Header erlauben: 

header('Access-Control-Allow-Origin: https://meine-domain.de');
header('Access-Control-Allow-Methods: POST, GET, OPTIONS');
header('Access-Control-Allow-Headers: Content-Type');

Bei bestimmten Requests (eigene Header, Content-Type: application/json, Methoden wie PUT oder DELETE) schickt der Browser vorher automatisch einen Preflight-Request mit der Methode OPTIONS. Antwortet der Server darauf nicht korrekt, kommt der eigentliche Request gar nicht erst an.

Wichtig zur Einordnung: CORS ist ein Schutz des Browsers, keine Serversicherheit. Mit curl oder Postman greift er nicht – der Server muss also trotzdem selbst prüfen, wer da anfragt. Und Access-Control-Allow-Origin: * funktioniert nicht zusammen mit Cookies; dafür braucht es eine konkrete Domain plus credentials: 'include'.

Fehlerbehandlung

  • fetch wirft bei HTTP-Fehlern keinen Fehler. Ein 404 oder 500 landet nicht im catch-Block, sondern liefert eine Response mit ok === false. Ohne die Prüfung auf response.ok wird eine Fehlerseite stillschweigend als Erfolg behandelt.
  • Der Benutzer sieht nichts. Scheitert ein Request, passiert ohne eigene Behandlung einfach gar nichts – der Fehler steht nur in der Konsole. Jede AJAX-Interaktion braucht eine sichtbare Rückmeldung.
  • Kein Ladezustand. Ohne Spinner oder deaktivierten Button wirkt die Seite eingefroren, und der Benutzer klickt mehrfach.
  • Zeitüberschreitungen kennt fetch nicht von sich aus. Nötig ist ein AbortController: 
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), 8000);

try {
  const res = await fetch(url, { signal: controller.signal });
} catch (e) {
  if (e.name === 'AbortError') { /* Timeout */ }
} finally {
  clearTimeout(timeout);
}

Race Conditions und zu viele Requests

Bei einer Live-Suche wird pro Tastendruck ein Request ausgelöst. Das erzeugt nicht nur unnötige Last, sondern auch ein echtes Problem: die Antworten kommen nicht zwingend in der Reihenfolge zurück, in der sie abgeschickt wurden. Die langsamere Antwort zu "Kam" kann nach der zu "Kaminofen" eintreffen und das korrekte Ergebnis wieder überschreiben.

Die zwei Gegenmittel:

  • Debouncing – erst senden, wenn der Benutzer kurz aufgehört hat zu tippen
  • Abbrechen – den vorherigen Request per AbortController verwerfen, bevor der neue startet 
let timer, controller;

input.addEventListener('input', () => {
  clearTimeout(timer);
  timer = setTimeout(async () => {
    controller?.abort();                 // alten Request verwerfen
    controller = new AbortController();
    const res = await fetch(`/suche.php?q=${encodeURIComponent(input.value)}`,
                            { signal: controller.signal });
    render(await res.json());
  }, 300);
});

Außerdem gilt: ein Klick, der mehrfach ausgelöst werden kann, sendet auch mehrfach. Den Button während des Requests deaktivieren – serverseitig zusätzlich auf Dubletten prüfen, denn auf den Client ist kein Verlass.

Browser-Historie und Deep Links

Wird Inhalt per AJAX ausgetauscht, ändert sich die URL nicht. Folgen: der Zurück-Button verlässt die Seite komplett statt einen Schritt zurückzugehen, ein Reload zeigt wieder den Ausgangszustand, und der Zustand lässt sich nicht als Link weitergeben oder als Lesezeichen speichern.

Lösung ist die History API: bei jedem Zustandswechsel die URL mitschreiben und auf das Zurückgehen reagieren. 

history.pushState({ kategorie }, '', `?kategorie=${kategorie}`);

window.addEventListener('popstate', (e) => {
  ladeProdukte(e.state?.kategorie ?? 'alle');
});

Damit ein geteilter Link auch funktioniert, muss der Server denselben Zustand zusätzlich serverseitig ausliefern können.

SEO und Crawler

Inhalte, die erst per AJAX nachgeladen werden, stehen nicht im ausgelieferten HTML. Suchmaschinen führen zwar JavaScript aus, aber verzögert und nicht garantiert vollständig – andere Crawler und Link-Vorschauen (Social Media, Messenger) gar nicht. Inhalte, die gefunden werden sollen, gehören deshalb ins initiale HTML oder brauchen Server-Side Rendering. AJAX eignet sich für Interaktion, nicht für den Hauptinhalt einer Seite.

Barrierefreiheit

Ein Screenreader bemerkt nicht von selbst, dass sich ein Teil der Seite geändert hat – beim klassischen Seitenwechsel wäre das durch den Neuaufbau automatisch passiert. Nötig sind deshalb aria-live-Bereiche für Statusmeldungen und ein bewusstes Setzen des Fokus auf den neuen Inhalt. Sonst arbeitet die Seite scheinbar ohne Reaktion. 

<div id="meldung" role="status" aria-live="polite"></div>

Abhängigkeit von JavaScript

Ist JavaScript deaktiviert, blockiert oder schlägt das Skript mit einem Fehler fehl, funktioniert die Interaktion gar nicht mehr. Der robuste Ansatz ist Progressive Enhancement: das Formular funktioniert als normales HTML-Formular mit action und method, und AJAX wird nur zusätzlich daraufgelegt. Genau das leistet e.preventDefault() im submit-Handler – ohne JavaScript greift der normale Weg.

Sicherheit

  • Ein AJAX-Endpunkt ist eine öffentliche URL. Er lässt sich direkt aufrufen, mit beliebigen Parametern, beliebig oft. Jede Validierung und jede Rechteprüfung muss deshalb serverseitig stattfinden – clientseitige Prüfung ist reiner Komfort.
  • CSRF – auch AJAX-Requests senden Cookies mit und brauchen daher ein Token. Zusätzlich hilft SameSite=Lax beim Session-Cookie.
  • XSS – Daten aus der Antwort niemals per innerHTML einsetzen, ohne sie zu escapen. textContent ist die sichere Variante.
  • Keine Zugangsdaten im Frontend. Alles im JavaScript ist einsehbar. API-Keys gehören hinter einen eigenen serverseitigen Endpunkt, der als Proxy dient.
  • Rate Limiting – ein offener Endpunkt, der Mails verschickt oder Datenbankabfragen auslöst, wird sonst zum Einfallstor für Spam und Überlastung.
  • Fehlerdetails nicht in die JSON-Antwort schreiben – Stacktraces und SQL-Fehler verraten die interne Struktur.

Caching

GET-Requests können von Browser und Proxys zwischengespeichert werden, was bei dynamischen Daten zu veralteten Ergebnissen führt. Abhilfe schaffen passende Cache-Control-Header auf dem Server, cache: 'no-store' in fetch oder ein Zeitstempel als zusätzlicher Parameter. Umgekehrt ist Caching bei Daten, die sich selten ändern, ausdrücklich erwünscht.

Weitere typische Stolpersteine

  • Statisches Hosting – auf GitHub Pages und ähnlichen Hostern wird kein PHP ausgeführt. Ein AJAX-Request an eine .php-Datei liefert dort den Quelltext oder einen 404. Deshalb funktionieren die Formular-Beispiele dieser Knowledge Base nur lokal über php -S localhost:8000.
  • Mixed Content – eine Seite über HTTPS darf keine Requests an http:// senden; der Browser blockiert sie.
  • Relative Pfade – ein fetch('api.php') löst relativ zur aktuellen URL auf, nicht relativ zur Skriptdatei. Nach einem Verzeichniswechsel zeigt der Pfad ins Leere.
  • Event-Handler auf nachgeladenem Inhalt – per AJAX eingefügte Elemente haben keine Listener aus dem ursprünglichen Setup. Lösung ist Event Delegation: den Listener auf einen bestehenden Container legen und über event.target auswerten.
  • Speicherverhalten – Listener und Timer auf entferntem DOM müssen aufgeräumt werden, sonst wachsen sie bei jedem Nachladen weiter an.
  • Offline und schlechtes Netz – mobil scheitern Requests regelmäßig. Ein Wiederholungsversuch und eine klare Meldung gehören dazu.

Abgrenzung zu anderen Verfahren

AJAX wird immer vom Client angestoßen. Sollen Aktualisierungen vom Server ausgehen, führen folgende Wege weiter:

  • Polling – der Client fragt in festen Abständen nach. Einfach umzusetzen, erzeugt aber viele unnötige Requests.
  • Long Polling – der Server hält die Anfrage offen, bis es etwas zu melden gibt. Spart Requests, bindet aber Verbindungen.
  • Server-Sent Events (SSE) – eine dauerhafte Verbindung, über die der Server in eine Richtung sendet. Ideal für Benachrichtigungen und Live-Ticker.
  • WebSockets – dauerhafte Verbindung in beide Richtungen, für Chat, Live-Daten und Mehrbenutzeranwendungen.

Faustregel: für einmalige Datenabrufe auf Benutzeraktion ist AJAX richtig; für laufende Aktualisierungen vom Server sind SSE oder WebSockets die passende Wahl.
