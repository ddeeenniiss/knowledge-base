Software Pattern

Ein Software Pattern ist eine bewährte Lösungsschablone für wiederkehrende Problemstellungen. Diese kann für eigene Projekte in der Regel problemlos übernommen werden.

Model View Controller (MVC)

Das MVC ist ein Entwurfsmodell, welches eine Anwendung in drei Teile unterteilt: Das Datenmodell (model), die Präsentation (view) und den Kontrollmechanismus (controller)

Das Modell (model) enthält die anzuzeigenden Daten (Listeneinträge, Text, die Beschriftung einer Schaltfläche usw.). Von außen kann man die Daten über dafür vorhergesehene Methoden erfragen und Änderungswünsche bekannt geben, die vom Modell allerdings auch abgelehnt werden können.

Die Ansicht (view) stellt die Daten in der Overfläche dar, sie ist der sichtbare Teil der GUI-Komponente im MVC Muster und für die Erscheinung (Größe, Farbe, Position usw.) zuständig. Die anzuzeigenden Daten werden durch die Ansicht vom Modell erfragt.

Die Steuerung (controller) empfängt Benutzeraktionen (Tastatureingaben, Mausklicks usw) und verarbeitet sie in Form von Botschaften an Ansicht und Modell.

Template Engines

Eine Template Engine ist die Verbindung zwischen Daten aus dem Backend und dem HTML, das im Browser landet. Die Template Engine ersetzt die Platzhalter und erzeugt daraus HTML. Bei Typo ist das beispielsweise Fluid. Bei Redaxo gibt es wiederum eigene Redaxo Templates

Software Qualität

Wichtige Aspekte beim coding sind Änderbarkeit, Effizienz, Übertragbarkeit, Zuverlässigkeit, Funktionalität und Benutzbarkeit

DRY – Don't Repeat Yourself

Code sollte nicht unnötig mehrfach geschrieben werden. Wiederkehrende Logik sollte beispielsweise in Funktionen, Komponenten oder Modulen zusammengefasst werden.

KISS – Keep It Simple, Stupid

Code sollte möglichst einfach und verständlich gehalten werden. Unnötige Komplexität, verschachtelte Logik und überkomplizierte Lösungen sollten vermieden werden.

Modularität

Ein Programm sollte in kleine, voneinander möglichst unabhängige Module aufgeteilt werden. Dadurch kann Code leichter verstanden, getestet, wiederverwendet und verändert werden.

Single Responsibility

Eine Funktion, Klasse oder Komponente sollte möglichst nur eine klar definierte Aufgabe haben. Änderungen an einer Aufgabe sollten dadurch möglichst wenige andere Programmteile beeinflussen.

Separation of Concerns

Unterschiedliche Verantwortlichkeiten sollten voneinander getrennt werden. In der Webentwicklung werden beispielsweise Struktur (HTML), Darstellung (CSS) und Logik (JavaScript) getrennt.

Wiederverwendbarkeit

Code sollte so gestaltet werden, dass Funktionen, Komponenten und Module an mehreren Stellen verwendet werden können, anstatt dieselbe Funktionalität mehrfach zu implementieren.

Lesbarkeit

Code sollte für andere Entwickler leicht verständlich sein. Aussagekräftige Variablennamen, eine sinnvolle Struktur und eine einheitliche Formatierung verbessern die Lesbarkeit.

Keine unnötigen globalen Variablen

Globale Variablen sollten möglichst vermieden werden, da sie zu unerwarteten Seiteneffekten und schwer nachvollziehbaren Abhängigkeiten führen können. Daten sollten bevorzugt lokal gehalten oder gezielt über Parameter und Rückgabewerte übertragen werden.

YAGNI – You Aren't Gonna Need It

Funktionalität sollte erst implementiert werden, wenn sie tatsächlich benötigt wird. Dadurch wird vermieden, dass unnötiger Code und unnötige Komplexität entstehen.

Fail Fast

Fehler sollten möglichst früh erkannt und behandelt werden. Ungültige Eingaben oder Zustände sollten beispielsweise frühzeitig überprüft werden, anstatt später schwer nachvollziehbare Fehler zu verursachen.

Defensive Programmierung

Programme sollten auch mit unerwarteten oder ungültigen Eingaben umgehen können. Eingaben werden beispielsweise validiert und potenzielle Fehlerfälle werden berücksichtigt.

Security by Design

Sicherheit sollte bereits bei der Entwicklung berücksichtigt werden. Dazu gehören beispielsweise Eingabevalidierung, Schutz vor XSS und SQL-Injection sowie ein sicherer Umgang mit Passwörtern und Authentifizierungsdaten.

Separation von Frontend und Backend

Frontend und Backend sollten klar getrennte Verantwortlichkeiten haben. Das Frontend kümmert sich hauptsächlich um Benutzeroberfläche und Interaktion, während das Backend beispielsweise Geschäftslogik, Datenverarbeitung und Datenbankzugriffe übernimmt.

Versionskontrolle

Änderungen am Code sollten mit einem Versionsverwaltungssystem wie Git nachvollziehbar gespeichert werden. Dadurch können Änderungen verglichen, zurückgesetzt und im Team gemeinsam bearbeitet werden.

Code Reviews

Code sollte nach Möglichkeit von anderen Entwicklern überprüft werden. Dadurch können Fehler, Sicherheitsprobleme und Verbesserungsmöglichkeiten früh erkannt werden.

Testbarkeit

Code sollte so geschrieben werden, dass einzelne Funktionen und Komponenten möglichst einfach getestet werden können. Kleine, klar abgegrenzte Funktionen erleichtern beispielsweise automatisierte Tests.

Dokumentation

Komplexe oder nicht offensichtliche Teile des Codes sollten dokumentiert werden. Der Code selbst sollte jedoch möglichst selbsterklärend sein, sodass unnötige Kommentare vermieden werden.

Konsequente Namensgebung

Variablen, Funktionen, Klassen und Komponenten sollten aussagekräftige und einheitliche Namen besitzen. Namen sollten möglichst klar erkennen lassen, welche Aufgabe oder welchen Inhalt sie repräsentieren.

Keine vorzeitige Optimierung

Code sollte zunächst korrekt und verständlich implementiert werden. Optimierungen sollten gezielt dort vorgenommen werden, wo tatsächlich ein Performanceproblem besteht.

Fehlerbehandlung

Fehler sollten kontrolliert behandelt werden, anstatt sie zu ignorieren. Benutzer sollten verständliche Fehlermeldungen erhalten, während technische Details beispielsweise für das Logging aufgezeichnet werden können.

Design by Contract

Design by Contract (DbC) ist ein Konzept der Softwareentwicklung, bei dem Softwarekomponenten durch Verträge festlegen, welche Bedingungen vor und nach ihrer Ausführung gelten müssen. Dazu gehören Vorbedingungen, Nachbedingungen und Invarianten. Dadurch werden Erwartungen und Garantien klar definiert und Fehler können frühzeitig erkannt werden.

Unified Modeling Language (UML)

Die Unified Modeling Language (UML) ist eine standardisierte grafische Modellierungssprache zur Planung, Darstellung und Dokumentation von Softwaresystemen. Sie wird im Software Engineering verwendet, um beispielsweise Klassen, Benutzerinteraktionen, Abläufe und Prozesse übersichtlich darzustellen. Zu den wichtigsten UML-Diagrammen gehören Klassen-, Use-Case-, Sequenz- und Aktivitätsdiagramme.
