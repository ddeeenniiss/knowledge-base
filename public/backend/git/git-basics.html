Git ist ein Versionskontroll System, dass Änderungen in Schritten als Commits in einem Historienbaum sammeln, so kann immer eingesehen werden wer zu welchem Zeitpunkt welche Änderung gemacht hat.

Aus Ordner ein Git-Repository machen:

Das macht man mit git init. Damit wird myproject/.git erstellt, indem commit-history, branches, konfigurationen, logs, referenzen, HEAD und Objekte stehen. Danach funktionieren git add, commit, branch etc. Bei einem clone wird das nicht benötigt, dann ist bereits .git enthalten.

Alle Einstellungen einsehen:

git config --list

Branches

Ein branch ist ein Verweis auf einen bestimmten commit. Er sichert die Arbeit, die in diesen commit & den Vorgängern steckt. Ein default Hauptbranch wird meist main genannt bzw früher master.

Branchnamen einsehen

mit git branch lassen sich alle branches anzeigen

mit git branch newBranch erstellt sich ein neuer branch mit Name newBranch.

mit git branch -m production benennt man den aktuellen branch zu production um

auf remote bringt man das ganze mit git push -u origin "branchname"

Branch umbenennen

git branch -m old-name new-name

Status abrufen:

git status zeigt den aktuellen Branch an, welche Änderungen zum commit vorgemerkt sind (gestaged / Staging Area) und welche nicht.

Was bedeutet unstaged, staged, untracked, tracked?

Begriff: Bedeutung:
unstagedNicht zum commit vorgemerkt / kein git add ausgeführt
stagedZum commit vorgemerkt / git add ausgeführt
untrackedDatei ist git noch nicht bekannt. Muss erst commitet werden.
trackedDatei wurde committet und ist git nun bekannt.

Commit eines anderen Branches übernehmen:

Mit git cherry-pick lassen sich commits eines anderen Branches auf den aktuell ausgechekten Branch übernehmen. git cherry-pick commitHash

git log

Mit git log lassen sich alle Hashes der letzten commits auflisten.

Dabei ist HEAD->production der aktuelle lokale Stand

origin/production ist der letzte bekannte Stand des Branches production auf Remote Repository

Insgesamt sind alle aufgelisteten Branches (2 lokal und 2 remote) auf dem selben Stand.

Dach Operator ^

main^ = direkter Vorgänger des commits, auf den main zeigt

main^^ = Vorvorgänger des commits, auf den main zeigt

Tilde Operator ~

geht eine Anzahl n an Schritten zurück, zB git checkout HEAD~4 für 4 commits zurück.

Änderungen rückgängig machen:

Sind die Änderungen noch nicht auf dem Remote Repository, also nicht gepushed, dann empfiehlt sich:

git reset --soft HEAD^

git reset bewegt den Zeiger zurück und kann commits verschwinden lassen.

Dabei kann unterschieden werden zwischen git reset

  • --soft: letzter commit wird entfernt und Änderungen bleiben gestaged
  • --mixed: letzter commit wird entfernt und Änderungen bleiben nicht gestaged
  • --hard: letzter commit wird entfernt und Änderungen sind entfernt

sollten die Änderungen bereits gepushed sein so empfiehlt sich keine Änderung der Historie, sondern:

git revert

erstellt einen neuen commit, der einen alten commit rückgängig macht

Projekt klonen

Um ein Projekt aus einem Git-Remote-Repository zu klonen, verwende den folgenden Befehl:

git clone repository-url

Ersetze repository-url durch die URL des Git-Repositorys, das du klonen möchtest. Zum Beispiel:

git clone https://gitlab.com/username/repository.git

Dieser Befehl erstellt ein Verzeichnis mit dem Namen des Repositorys und lädt den gesamten Inhalt des Repositorys in dieses Verzeichnis.

Commits erstellen

Ein Commit ist immer ein Snapshot der aktuellen Änderungen, die auf das local Repository übertragen werden. Wir wollen unsere Commits immer übersichtlich erstellen, daher ein paar Grundregeln:

Lade deine Änderungen immer in kleinen abgeschlossenen Paketen hoch, in denen die Änderung klar definiert ist.

Schreibe deine Änderung kurz und knapp in die Commit-Message.

Füge den Link zum Asana-Ticket in die Commit-Message ein

Schreibe deine Commits auf englisch.

Beispiel: Style: Add more padding to container of text module. #asanaTicketLink

Um Änderungen in dein entferntes Repository hochzuladen, verwende den Befehl git push. Wenn du sicherstellen möchtest, dass dein lokaler Branch auf dem neuesten Stand ist und keine Konflikte auftreten, kannst du die Optionen rebase und autostash verwenden.

git rebase

mit git rebase -i zeigt Git jedem einzelnen commit, der durch rebase kopiert werden würde (Hashes & Kommentare).

mit git -i HEAD~3 können die letzten 3 commits neu geordnet werden und auch gedropt (gelöscht) werden.

Im vim Editor muss für das bearbeiten i für insert mode eingegeben werden.

Der Befehl git push mit den Optionen rebase und autostash sieht wie folgt aus:

git pull --rebase --autostash

Git Commit Nachrichten immer nach folgendem Schema:

  • Feat: Neues Feature (Funktionalität für User, die Seite kann danach mehr)
  • Fix: Fehlerbehebung
  • Refactor: Umstrukturierung des Codes ohne Verhaltensänderung
  • Docs: Dokumentationsänderungen
  • Module: Neues Modul erstellt
  • Chore: Projekt Konfiguration geändert / package.json geändert
  • Style: Stylingänderungen
  • Revert: Einzelne Schritte rückgängig machen

--rebase: Diese Option sorgt dafür, dass deine lokalen Änderungen auf die neuesten Änderungen im entfernten Repository angewendet werden. Dadurch wird eine saubere, lineare Historie erstellt.

--autostash: Diese Option speichert automatisch deine lokalen Änderungen, bevor der Rebase-Prozess beginnt, und stellt sie danach wieder her. Das ist besonders nützlich, wenn du ungespeicherte Änderungen hast.

Feature-Branches

Oft sollen neue funktionen implementiert werden, welche nicht direkt live gehen sollen. Dafür eignen sich sogenannte feature-Branches. Soll ein solches feature angelegt werden, wird ein neuer Branch feature/feature-name angelegt.

Nachdem ein Feature getestet und fertig für den Livegang ist, wird es in den main-Branch gemerged.

Branch wechseln:

mit git checkout branchName wird der branch gewechselt. Dabei wird HEAD auf den angegebenen Branch gesetzt und das Working Directory wird auf den Stand dieses Branches aktualisiert. HEAD ist immer ein Zeiger auf den aktuell ausgecheckten Branch (HEAD -> production). Production zeigt wiederum auf einen commit. Dieser ist immer mit * gekennzeichnet.

Sonderfall: Detached HEAD: Wenn direkt ein commit ausgecheckt wird (git checkout a238fds), dann zeigt HEAD direkt auf diesen Commit (HEAD -> a238fds). Dann ist man nicht mehr auf einem branch, somit wären neue commits losgelöst.

Rebase und Merge

Da wir Merge-Commits in unserer Git-Historie vermeiden wollen, müssen die merges auf eine ganz bestimmte Weise vorgenommen werden.

Bei einem merge wird immer ein externer branch zum aktuellen branch gemerged. Ich befinde mich also auf dem branch, auf dem ich etwas von einem anderen branch haben will.

Wichtig ist dabei, dass immer ein Rebase durchgeführt wird, damit werden Konflikte weitestgehend vermieden.

Branches zusammenzuführen

Die Branches, welche gemerged werden sollen auf den aktuellen Stand bringen

git checkout master
git pull
git checkout feature/example
git pull

Rebase den feature-Branch auf den neuesten Stand von master

git rebase master --no-verify

Wechsel zurück zum master Branch und führe einen Fast-Forward Merge durch, um die Änderungen vom feature Branch in master zu integrieren

git checkout master
git merge --ff-only feature/example
git push

Lösche den lokalen und den Remote feature Branch

git branch -D feature/example
git push origin --delete feature/example
