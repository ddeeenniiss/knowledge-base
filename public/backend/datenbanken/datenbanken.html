Datenbanken

Eine Datenbank ist eine strukturierte, dauerhafte Sammlung von Daten, auf die mehrere Benutzer und Programme gleichzeitig zugreifen können. Der Unterschied zu einer einfachen Datei liegt nicht im Speichern selbst, sondern in dem, was drumherum passiert: gleichzeitige Zugriffe werden koordiniert, Daten auf Gültigkeit geprüft, Abfragen optimiert, Berechtigungen durchgesetzt und bei einem Absturz wird ein konsistenter Zustand wiederhergestellt. Genau das leistet eine Datei nicht.

DBMS (Datenbankmanagementsystem)

Das DBMS ist die Software, die die Datenbank verwaltet. Es liegt zwischen Anwendung und Datenbestand: die Anwendung stellt eine Anfrage (meist in SQL), das DBMS entscheidet, wie es die Daten tatsächlich liest oder schreibt, und liefert das Ergebnis zurück. Die Anwendung muss also nicht wissen, in welchen Dateien und in welcher Reihenfolge die Daten auf der Festplatte liegen.

Begriffe, die oft vermischt werden:

  • Datenbank (DB) – der Datenbestand selbst
  • DBMS – die verwaltende Software (z.B. MySQL, Oracle)
  • Datenbanksystem (DBS) – beides zusammen: DBMS + Datenbank
  • RDBMS – ein relationales DBMS, also eines, das Daten in Tabellen mit Beziehungen organisiert

Die zentralen Aufgaben eines DBMS:

  • Datendefinition – Strukturen anlegen und ändern (Tabellen, Spalten, Datentypen)
  • Datenmanipulation – Einfügen, Lesen, Ändern, Löschen
  • Integrität – Regeln erzwingen: Pflichtfelder, eindeutige Werte, gültige Verweise zwischen Tabellen
  • Mehrbenutzerbetrieb – parallele Zugriffe über Sperren (Locking) und Transaktionen koordinieren, sodass sich Benutzer nicht gegenseitig die Daten zerstören
  • Zugriffsschutz – Benutzer, Rollen und Rechte
  • Recovery – Wiederherstellung nach Absturz über Transaktionslogs
  • Optimierung – der Query-Optimizer entscheidet selbständig, welchen Weg eine Abfrage nimmt und welche Indizes genutzt werden
  • Redundanzvermeidung – Daten liegen idealerweise nur an einer Stelle

Ein wichtiger Nebeneffekt ist die Datenunabhängigkeit: die Anwendung spricht nur über SQL mit dem DBMS, sodass sich interne Speicherstrukturen ändern können, ohne dass der Anwendungscode angepasst werden muss.

ACID

ACID beschreibt die vier Garantien, die ein relationales DBMS für Transaktionen gibt – also für eine Gruppe von Anweisungen, die nur gemeinsam gültig sind (Klassiker: eine Überweisung besteht aus Abbuchen und Gutschreiben).

  • Atomicity (Atomarität) – eine Transaktion wird vollständig oder überhaupt nicht ausgeführt. Bricht sie mitten ab, wird alles zurückgerollt.
  • Consistency (Konsistenz) – vor und nach der Transaktion sind alle Regeln der Datenbank erfüllt.
  • Isolation – parallele Transaktionen beeinflussen sich nicht gegenseitig; jede arbeitet, als wäre sie allein.
  • Durability (Dauerhaftigkeit) – bestätigte Änderungen bleiben erhalten, auch bei Stromausfall oder Absturz.

Das relationale Modell

Relationale Datenbanken speichern Daten in Tabellen (Relationen). Eine Zeile (Datensatz, Tupel) ist ein Objekt, eine Spalte (Attribut, Feld) eine Eigenschaft mit festem Datentyp.

  • Primärschlüssel (Primary Key) – identifiziert eine Zeile eindeutig, meist eine automatisch hochzählende id-Spalte
  • Fremdschlüssel (Foreign Key) – verweist auf den Primärschlüssel einer anderen Tabelle und stellt damit die Beziehung her. Die Datenbank verhindert dann Verweise auf nicht existierende Datensätze (referentielle Integrität).
  • Unique – Werte dürfen nur einmal vorkommen (z.B. E-Mail-Adresse)
  • NOT NULL – Pflichtfeld
  • Index – Zusatzstruktur, die das Suchen beschleunigt

Beziehungen zwischen Tabellen:

  • 1:1 – ein Benutzer hat genau ein Profil. Der Fremdschlüssel liegt in einer der beiden Tabellen und ist unique.
  • 1:n – eine Kategorie hat viele Produkte. Der häufigste Fall; der Fremdschlüssel liegt immer auf der n-Seite (also in products.category_id).
  • n:m – ein Produkt hat mehrere Tags, ein Tag gehört zu mehreren Produkten. Lässt sich nicht direkt abbilden und braucht eine Zwischentabelle (product_tag mit product_id und tag_id).

Normalisierung

Normalisierung ist das Aufteilen von Tabellen, um Redundanz und damit Widersprüche zu vermeiden. Steht der Kundenname in jeder Bestellzeile, muss er bei einer Namensänderung überall gepflegt werden – und irgendeine Stelle wird vergessen.

  • 1. Normalform (1NF) – jedes Feld enthält nur einen einzelnen Wert, keine Listen wie "rot,grün,blau" in einer Spalte
  • 2. Normalform (2NF) – 1NF, und jedes Nicht-Schlüssel- Attribut hängt vom vollständigen Primärschlüssel ab
  • 3. Normalform (3NF) – 2NF, und kein Attribut hängt von einem anderen Nicht-Schlüssel-Attribut ab (keine transitiven Abhängigkeiten, z.B. Postleitzahl → Ort in einer Kundentabelle)

In der Praxis normalisiert man bis zur 3NF und weicht nur bewusst davon ab (Denormalisierung), wenn Lesegeschwindigkeit wichtiger ist als Redundanzfreiheit – etwa bei Auswertungen und Reporting.

SQL (Structured Query Language)

SQL ist die standardisierte Sprache, mit der mit relationalen Datenbanken gesprochen wird. Sie ist deklarativ: man beschreibt, was man haben möchte, nicht wie es beschafft wird. Der Standard ist ANSI/ISO-normiert, jedes DBMS hat aber eigene Erweiterungen – reines SQL ist nur begrenzt portabel.

SQL wird in Teilsprachen gegliedert:

  • DDL (Data Definition Language) – Struktur: CREATE, ALTER, DROP, TRUNCATE
  • DML (Data Manipulation Language) – Daten: INSERT, UPDATE, DELETE
  • DQL (Data Query Language) – Abfragen: SELECT
  • DCL (Data Control Language) – Rechte: GRANT, REVOKE
  • TCL (Transaction Control Language) – Transaktionen: START TRANSACTION, COMMIT, ROLLBACK

Schlüsselwörter sind nicht case-sensitive, werden aber per Konvention großgeschrieben. Jede Anweisung endet mit einem Semikolon.

Tabellen anlegen (DDL)

CREATE DATABASE shop
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE TABLE categories (
  id    INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name  VARCHAR(100) NOT NULL
);

CREATE TABLE products (
  id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  category_id INT UNSIGNED NOT NULL,
  name        VARCHAR(255) NOT NULL,
  price       DECIMAL(10,2) NOT NULL DEFAULT 0,
  active      TINYINT(1) NOT NULL DEFAULT 1,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_products_category
    FOREIGN KEY (category_id) REFERENCES categories(id)
    ON DELETE RESTRICT,
  INDEX idx_products_name (name)
);

ALTER TABLE products ADD COLUMN sku VARCHAR(50) NULL AFTER name;
ALTER TABLE products MODIFY COLUMN price DECIMAL(12,2) NOT NULL;
DROP TABLE products;

DROP löscht die Tabelle samt Struktur, TRUNCATE nur den Inhalt (schnell, ohne Rollback), DELETE löscht Zeilen einzeln und ist zurückrollbar.

Die wichtigsten Datentypen (MySQL/MariaDB-Schreibweise):

  • INT, BIGINT, TINYINT – Ganzzahlen, TINYINT(1) wird als Boolean genutzt
  • DECIMAL(10,2) – exakte Dezimalzahl, Pflicht für Geldbeträge. FLOAT und DOUBLE rechnen ungenau und sind dafür ungeeignet.
  • VARCHAR(n) – Text variabler Länge, CHAR(n) feste Länge, TEXT für lange Inhalte
  • DATE, DATETIME, TIMESTAMP (zeitzonenabhängig), TIME, YEAR
  • ENUM – feste Werteliste, JSON – ganze JSON-Dokumente, BLOB – Binärdaten

Daten abfragen (SELECT)

SELECT name, price FROM products;
SELECT * FROM products WHERE active = 1;

-- Filtern
WHERE price > 100 AND category_id = 3
WHERE name LIKE 'Ofen%'          -- % = beliebig viele Zeichen
WHERE category_id IN (1, 2, 5)
WHERE price BETWEEN 50 AND 200
WHERE sku IS NULL                -- niemals = NULL verwenden!

-- Sortieren und begrenzen
SELECT * FROM products ORDER BY price DESC, name ASC LIMIT 10 OFFSET 20;

-- Doppelte entfernen
SELECT DISTINCT category_id FROM products;

NULL bedeutet "unbekannt" und verhält sich eigen: NULL = NULL ergibt nicht true, sondern unbekannt. Deshalb immer IS NULL bzw. IS NOT NULL verwenden.

Aggregation und Gruppierung

SELECT COUNT(*) FROM products;
SELECT AVG(price), MIN(price), MAX(price), SUM(price) FROM products;

SELECT category_id, COUNT(*) AS anzahl, AVG(price) AS schnitt
FROM products
WHERE active = 1          -- filtert Zeilen VOR der Gruppierung
GROUP BY category_id
HAVING COUNT(*) > 5       -- filtert Gruppen NACH der Gruppierung
ORDER BY anzahl DESC;

Der Unterschied zwischen WHERE und HAVING ist eine klassische Prüfungsfrage: WHERE wirkt auf einzelne Zeilen vor dem Gruppieren, HAVING auf die gebildeten Gruppen danach. Die logische Ausführungsreihenfolge ist FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT – nicht die Schreibreihenfolge.

JOINs

Ein JOIN verbindet Zeilen aus mehreren Tabellen über eine Bedingung, üblicherweise Fremdschlüssel auf Primärschlüssel.

  • INNER JOIN – nur Zeilen, die in beiden Tabellen eine Entsprechung haben
  • LEFT JOIN – alle Zeilen der linken Tabelle, fehlende rechte Werte werden NULL
  • RIGHT JOIN – umgekehrt
  • FULL OUTER JOIN – alle Zeilen beider Seiten. MySQL und MariaDB kennen das nicht und brauchen ein UNION aus LEFT und RIGHT JOIN.
  • CROSS JOIN – jede Zeile mit jeder (kartesisches Produkt), selten gewollt
  • SELF JOIN – Tabelle mit sich selbst, z.B. für Baumstrukturen 
SELECT p.name, c.name AS kategorie
FROM products p
INNER JOIN categories c ON c.id = p.category_id
WHERE p.active = 1;

-- Kategorien auch ohne Produkte anzeigen
SELECT c.name, COUNT(p.id) AS anzahl
FROM categories c
LEFT JOIN products p ON p.category_id = c.id
GROUP BY c.id, c.name;

Ein vergessenes ON erzeugt ein kartesisches Produkt – aus 1.000 × 1.000 Zeilen wird dann eine Million. Mit Subqueries (Unterabfragen) und UNION lassen sich Ergebnisse zusätzlich verschachteln bzw. zusammenführen.

Daten ändern (DML)

INSERT INTO products (category_id, name, price)
VALUES (1, 'Kaminofen', 1299.00);

-- mehrere Zeilen in einem Befehl (deutlich schneller)
INSERT INTO products (category_id, name, price) VALUES
  (1, 'Pelletofen', 2499.00),
  (2, 'Ofenrohr',     89.90);

UPDATE products SET price = 1199.00 WHERE id = 5;
DELETE FROM products WHERE active = 0;

Die wichtigste Regel überhaupt: UPDATE und DELETE ohne WHERE betreffen die gesamte Tabelle. Vor jedem Schreiben auf Produktivdaten erst dieselbe Bedingung mit SELECT testen und ein Backup haben.

Transaktionen

START TRANSACTION;

UPDATE konten SET saldo = saldo - 100 WHERE id = 1;
UPDATE konten SET saldo = saldo + 100 WHERE id = 2;

COMMIT;     -- beide Änderungen gemeinsam übernehmen
-- ROLLBACK; -- oder beide gemeinsam verwerfen

Transaktionen funktionieren nur mit einer Storage Engine, die sie unterstützt – bei MySQL/MariaDB also InnoDB, nicht MyISAM. Über Isolationslevel (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) wird gesteuert, wie stark parallele Transaktionen voneinander abgeschirmt sind.

Indizes und Performance

Ein Index ist eine sortierte Zusatzstruktur (meist ein B-Baum), über die die Datenbank Zeilen findet, ohne die ganze Tabelle zu lesen (Full Table Scan). Der Primärschlüssel ist automatisch indiziert.

  • Indizes gehören auf Spalten, die in WHERE, JOIN und ORDER BY vorkommen – also vor allem auf Fremdschlüssel.
  • Jeder Index kostet Speicher und bremst INSERT/UPDATE, weil er mitgepflegt werden muss. Nicht blind auf jede Spalte.
  • Ein Index auf einer Spalte mit sehr wenigen unterschiedlichen Werten (z.B. ein Ja/Nein-Feld) bringt kaum etwas.
  • Funktionen auf der Spalte verhindern die Indexnutzung: WHERE YEAR(created_at) = 2026 nutzt den Index nicht, ein Vergleich auf einen Datumsbereich schon.
  • Bei einem zusammengesetzten Index zählt die Reihenfolge – er wirkt nur von links beginnend. 
EXPLAIN SELECT * FROM products WHERE name = 'Kaminofen';
-- zeigt, ob ein Index genutzt wird und wie viele Zeilen gelesen werden

CREATE INDEX idx_products_category ON products (category_id);
SHOW INDEX FROM products;

Weitere Werkzeuge: das Slow Query Log protokolliert langsame Abfragen, ANALYZE TABLE aktualisiert die Statistiken des Optimizers. Ein häufiges Anwendungsproblem ist das N+1-Problem: statt einer Abfrage mit JOIN werden in einer Schleife hunderte Einzelabfragen ausgeführt.

Views, Stored Procedures und Trigger

  • View – gespeicherte Abfrage, die sich wie eine Tabelle verwenden lässt. Gut für wiederkehrende Auswertungen und um Komplexität zu verstecken.
  • Stored Procedure / Function – in der Datenbank gespeicherte Logik. Schnell, aber schwer zu versionieren und zu testen, daher in Webprojekten eher selten.
  • Trigger – läuft automatisch bei INSERT, UPDATE oder DELETE, z.B. für Protokolltabellen. Nebenwirkungen sind von außen nicht sichtbar, was die Fehlersuche erschwert. 
CREATE VIEW v_active_products AS
SELECT p.id, p.name, p.price, c.name AS kategorie
FROM products p
JOIN categories c ON c.id = p.category_id
WHERE p.active = 1;

SELECT * FROM v_active_products;

Relational oder NoSQL

Relationale Datenbanken brauchen ein festes Schema und garantieren ACID. NoSQL-Systeme verzichten teilweise darauf, um besser horizontal skalieren zu können (CAP-Theorem: bei einer Netzwerkpartition muss zwischen Konsistenz und Verfügbarkeit gewählt werden).

  • Dokumentorientiert – MongoDB, CouchDB. Speichert JSON-ähnliche Dokumente ohne festes Schema.
  • Key-Value – Redis, Memcached. Sehr schnell, typisch für Caching und Sessions.
  • Spaltenorientiert – Cassandra, HBase. Für sehr große Datenmengen und Analysen.
  • Graphdatenbanken – Neo4j. Für stark vernetzte Daten wie soziale Netzwerke.
  • Suchindizes – Elasticsearch. Für Volltextsuche.

Für klassische Webprojekte mit Bestellungen, Benutzern und Inhalten ist eine relationale Datenbank praktisch immer die richtige Wahl. NoSQL wird meist ergänzend eingesetzt, etwa Redis als Cache neben MySQL.

Bekannte Datenbanksysteme

Oracle Database

Oracle Database ist das klassische Enterprise-RDBMS, 1979 erschienen und im Großunternehmensumfeld, bei Banken, Versicherungen und in SAP-Landschaften weit verbreitet. Es gilt als technisch sehr ausgereift, ist aber komplex zu betreiben und teuer.

  • PL/SQL – eigene, mächtige Programmiersprache innerhalb der Datenbank für Prozeduren, Funktionen und Pakete
  • Sehr weitreichende Funktionen: Partitionierung, Materialized Views, Real Application Clusters (RAC) für Hochverfügbarkeit, Data Guard für Replikation, feingranulare Rechte und Auditing
  • Eigenheiten gegenüber MySQL: Standardport 1521, Sequences statt AUTO_INCREMENT, ROWNUM bzw. FETCH FIRST n ROWS statt LIMIT, die Dummy-Tabelle DUAL, NVL() statt IFNULL(), und ein "Schema" entspricht dort einem Benutzer
  • Lizenzierung – kostenpflichtig und meist nach CPU-Kernen abgerechnet, was schnell sehr teuer wird. Die kostenlose Express Edition (XE) ist in CPU, RAM und Datenmenge begrenzt und für Tests und Lernen gedacht.
  • Oracle ist außerdem seit der Sun-Übernahme 2010 Eigentümer von MySQL – der Grund, warum MariaDB entstanden ist.

Für Webprojekte spielt Oracle praktisch keine Rolle. Relevant wird es, wenn eine Anwendung an bestehende Unternehmenssysteme angebunden werden muss.

MySQL

MySQL ist das bekannteste Open-Source-RDBMS und über Jahrzehnte der Standard im Webumfeld gewesen – das "M" in den Abkürzungen LAMP (Linux, Apache, MySQL, PHP) und XAMPP. WordPress, Redaxo, TYPO3, Shopware und praktisch jedes PHP-CMS setzen darauf.

  • 1995 von MySQL AB entwickelt, 2008 an Sun verkauft, seit 2010 bei Oracle
  • Duales Lizenzmodell – Community Edition unter GPL, daneben kommerzielle Editionen mit Support und Zusatzfunktionen
  • Standardport 3306
  • Storage Engines sind austauschbar und ein MySQL-Spezifikum: InnoDB ist seit 5.5 Standard und beherrscht Transaktionen, Fremdschlüssel und Row-Level-Locking – MyISAM kann das alles nicht und sollte nur noch in Altbeständen vorkommen. Weitere: MEMORY, ARCHIVE, CSV.
  • Replikation (Master-Replica), Partitionierung, JSON-Spalten, Window Functions und CTEs (ab 8.0), Volltextsuche
  • Zeichensatz – immer utf8mb4 verwenden. Das ältere "utf8" in MySQL ist nur ein 3-Byte-UTF-8 und kann keine Emojis und manche Sonderzeichen speichern.

MariaDB

MariaDB ist ein 2009 gestarteter Fork von MySQL, begonnen von Michael "Monty" Widenius, einem der MySQL-Gründer, aus Sorge um die Zukunft des Projekts unter Oracle. Der Name kommt von seiner Tochter Maria – wie zuvor schon MySQL von My.

  • Vollständig Open Source (GPL), ohne kommerzielle Doppellizenz, und von einer Foundation getragen
  • Weitgehend drop-in-kompatibel: gleiche Protokolle, gleiche Befehle, gleicher Port 3306. Der Client heißt mariadb, mysql existiert als Alias – in vielen Linux-Distributionen ist unter dem Namen "mysql" längst MariaDB installiert.
  • Eigene Entwicklungen: zusätzliche Storage Engines (Aria, ColumnStore für Analysen, Spider), Galera Cluster für Multi-Master-Replikation, virtuelle Spalten, teils bessere Query-Optimierung
  • Standard in Debian, Ubuntu, RHEL und bei vielen Hostern; DDEV nutzt es üblicherweise ebenfalls

Wichtig: Die Versionsnummern laufen seit MySQL 8 auseinander, und die Kompatibilität ist nicht mehr vollständig – JSON- und Window-Function-Implementierungen, Authentifizierungs-Plugins und manche Systemtabellen unterscheiden sich. Ein Wechsel von MySQL zu MariaDB ist meist unproblematisch, der Weg zurück dagegen oft nicht. Für Dumps gilt deshalb: nicht einfach zwischen beiden hin- und herschieben, ohne es zu testen.

Weitere relevante Systeme

  • PostgreSQL – Open Source, gilt als technisch fortschrittlichste freie Datenbank: sehr standardtreu, starke Datentypen (JSONB, Arrays, Geodaten über PostGIS), Transaktionen auch für DDL. Standardport 5432. In modernen Projekten zunehmend erste Wahl statt MySQL.
  • SQLite – die gesamte Datenbank ist eine einzige Datei, kein Server nötig. Ideal für kleine Projekte, Tests, Apps und Embedded-Systeme; nicht für viele gleichzeitige Schreibzugriffe.
  • Microsoft SQL Server – im Windows-/.NET-Umfeld verbreitet, Abfragesprache T-SQL, Standardport 1433.
  • MongoDB – bekannteste dokumentorientierte NoSQL-Datenbank.
  • Redis – In-Memory Key-Value-Store für Caching, Sessions und Warteschlangen.

Arbeiten mit Datenbanken

Zugriffswege

  • Kommandozeile – mysql / mariadb / psql / sqlplus. Immer vorhanden, ideal auf dem Server und für Dumps.
  • Weboberfläche – phpMyAdmin (bei fast jedem Hoster vorinstalliert), Adminer (eine einzige PHP-Datei, sehr schlank)
  • Desktop-GUI – DBeaver (kostenlos, alle Systeme), MySQL Workbench, TablePlus, Sequel Ace, DataGrip, Oracle SQL Developer
  • Aus dem Code – in PHP über PDO (empfohlen) oder mysqli, immer mit Prepared Statements
  • ORM / Query Builder – Doctrine, Eloquent (Laravel), oder in Redaxo rex_sql. Bildet Tabellen auf Objekte ab und erspart handgeschriebenes SQL, erzeugt aber bei Unachtsamkeit ineffiziente Abfragen (N+1).

Verbinden und umsehen (MySQL / MariaDB)

# verbinden, Passwort interaktiv abfragen lassen
mysql -u root -p
mysql -h 127.0.0.1 -P 3306 -u shopuser -p shop

SHOW DATABASES;              -- welche Datenbanken gibt es?
USE shop;                    -- Datenbank auswählen
SHOW TABLES;                 -- welche Tabellen?
DESCRIBE products;           -- Spalten und Typen
SHOW CREATE TABLE products;  -- das vollständige CREATE-Statement
SHOW INDEX FROM products;
SELECT DATABASE(), VERSION(), USER();
SHOW PROCESSLIST;            -- laufende Abfragen
EXIT;

Das Passwort nie direkt im Befehl angeben (-pgeheim), da es sonst in der Shell-History und in der Prozessliste landet. Besser nur -p schreiben und warten, oder die Zugangsdaten in einer ~/.my.cnf mit Dateirechten 600 ablegen.

Benutzer und Rechte

CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE USER 'shopuser'@'localhost' IDENTIFIED BY 'sicheresPasswort';

-- nur die nötigen Rechte, nur auf die eine Datenbank
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'shopuser'@'localhost';

FLUSH PRIVILEGES;
SHOW GRANTS FOR 'shopuser'@'localhost';
REVOKE DELETE ON shop.* FROM 'shopuser'@'localhost';

Grundregel Least Privilege: pro Projekt ein eigener Benutzer mit genau den Rechten, die die Anwendung braucht – niemals der root-Benutzer in der Anwendungskonfiguration. Der Host-Teil ist Teil der Identität: 'user'@'localhost' und 'user'@'%' sind zwei verschiedene Benutzer.

Backup und Restore

# Dump einer Datenbank (SQL-Datei mit CREATE- und INSERT-Statements)
mysqldump -u root -p shop > shop_2026-10-21.sql
mariadb-dump -u root -p shop > shop.sql     # MariaDB-Name

# komprimiert
mysqldump -u root -p shop | gzip > shop.sql.gz

# nur Struktur / nur Daten
mysqldump --no-data   -u root -p shop > struktur.sql
mysqldump --no-create-info -u root -p shop > daten.sql

# alle Datenbanken
mysqldump --all-databases -u root -p > alles.sql

# Wiederherstellen (Datenbank muss existieren)
mysql -u root -p shop < shop_2026-10-21.sql
gunzip < shop.sql.gz | mysql -u root -p shop

Wichtige Punkte zum Thema Backup:

  • Ein Backup, das nie zurückgespielt wurde, ist kein Backup. Den Restore regelmäßig testen.
  • Vor jeder Migration und jedem größeren UPDATE einen Dump ziehen.
  • Dumps enthalten alle Daten im Klartext – sie gehören nicht ins Git und nicht in ein öffentlich erreichbares Verzeichnis (DSGVO).
  • Mit --single-transaction wird bei InnoDB ein konsistenter Dump erstellt, ohne die Tabellen zu sperren.
  • Für große Datenbanken sind physische Backups (Percona XtraBackup) oder Snapshots sinnvoller als Dumps.

Zeichensatz und Collation

Zeichensalat ("Ã¼" statt "ü") entsteht, wenn Datenbank, Tabelle, Verbindung und Anwendung nicht denselben Zeichensatz verwenden. Die Verbindung ist dabei die am häufigsten vergessene Stelle. 

-- überall utf8mb4
ALTER DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE products CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
SHOW VARIABLES LIKE 'character_set%';
// in PHP den Zeichensatz schon im DSN mitgeben
$pdo = new PDO('mysql:host=localhost;dbname=shop;charset=utf8mb4', $user, $pass);

Die Collation bestimmt zusätzlich Sortierung und Vergleich – utf8mb4_unicode_ci bzw. utf8mb4_general_ci ignorieren Groß- und Kleinschreibung ("ci" = case insensitive).

Konfiguration und Betrieb

  • Konfigurationsdatei: my.cnf bzw. /etc/mysql/my.cnf und die Dateien in conf.d. Wichtige Werte: innodb_buffer_pool_size (der größte Performance-Faktor, typisch 50–70 % des RAM auf einem dedizierten Server), max_connections, bind_address.
  • bind-address = 127.0.0.1 – die Datenbank sollte nicht aus dem Internet erreichbar sein. Zugriff von außen am besten über einen SSH-Tunnel.
  • mysql_secure_installation nach der Installation ausführen: root-Passwort setzen, anonyme Benutzer und Testdatenbank entfernen.
  • Dienst steuern: systemctl status/restart mariadb bzw. mysql.
  • Lokale Entwicklung läuft heute meist über DDEV oder Docker – dort ist die Datenbank ein eigener Container, Zugriff per ddev mysql, ddev import-db und ddev export-db.

Schemaänderungen versionieren (Migrationen)

Eine Datenbank lässt sich nicht wie Code einfach aus Git auschecken. Deshalb werden Strukturänderungen als Migrationen geschrieben: kleine, nummerierte Skripte, die nacheinander ausgeführt werden und mitversioniert sind.

  • Jede Änderung ist ein eigenes Skript, das nur vorwärts geht und nie nachträglich verändert wird.
  • Welche Migrationen gelaufen sind, merkt sich eine eigene Tabelle.
  • Werkzeuge: Doctrine Migrations, Phinx, Laravel Migrations – in Redaxo laufen Strukturänderungen über das jeweilige AddOn-Update.
  • ALTER TABLE sperrt bei großen Tabellen unter Umständen lange. Produktiv deshalb in einem Wartungsfenster oder mit Online-DDL arbeiten.

Sicherheit

  • SQL-Injection – niemals Benutzereingaben in einen SQL-String einsetzen. Immer Prepared Statements mit Platzhaltern (siehe PHP-Seite). Tabellen- und Spaltennamen lassen sich nicht binden und müssen gegen eine Whitelist geprüft werden.
  • Least Privilege – eigener Benutzer pro Projekt, kein root, keine DROP-Rechte für die Anwendung.
  • Zugangsdaten gehören in eine .env-Datei außerhalb des Webroots, nicht in den Code und nicht ins Git.
  • Passwörter in der Datenbank nur als Hash (password_hash), niemals im Klartext und nicht als md5.
  • Kein öffentlicher Port, Verbindungen nach außen über TLS, Datenbank-Backups verschlüsselt ablegen.
  • Fehlermeldungen nicht an den Benutzer ausgeben – sie verraten Tabellennamen und Struktur.

Typischer Arbeitsablauf

  • Modellieren – Entitäten, Attribute und Beziehungen festlegen, als ER-Diagramm skizzieren, bis zur 3NF normalisieren
  • Anlegen – Datenbank mit utf8mb4, Tabellen mit Primär- und Fremdschlüsseln, Indizes auf den Fremdschlüsseln
  • Benutzer mit minimalen Rechten einrichten und Zugangsdaten in die .env legen
  • Abfragen entwickeln – erst im GUI oder auf der Kommandozeile testen, dann in den Code übernehmen
  • Im Code ausschließlich Prepared Statements und Transaktionen für zusammenhängende Schreibvorgänge
  • Prüfen – EXPLAIN auf die wichtigen Abfragen, Slow Query Log beobachten, Indizes nachziehen
  • Strukturänderungen als Migration schreiben, vorher Dump ziehen
  • Backups automatisieren und den Restore testen

Häufige Fehler und ihre Ursache

  • Access denied for user – falsches Passwort, falscher Host-Teil des Benutzers oder fehlende Rechte
  • Unknown database – Datenbank existiert nicht oder ist falsch geschrieben
  • Can't connect to MySQL server – Dienst läuft nicht, falscher Port, oder 127.0.0.1 statt localhost nötig (bzw. umgekehrt, weil localhost über einen Socket verbindet)
  • Cannot add or update a child row: a foreign key constraint fails – der verwiesene Datensatz existiert nicht
  • Duplicate entry for key – Verstoß gegen einen Unique-Index oder den Primärschlüssel
  • Incorrect string value – Zeichensatz ist nicht utf8mb4
  • Deadlock found when trying to get lock – zwei Transaktionen blockieren sich; die Anwendung muss den Vorgang wiederholen
  • Lock wait timeout exceeded – eine Transaktion wurde offen gelassen, also kein COMMIT oder ROLLBACK
  • Table doesn't exist – unter Linux sind Tabellennamen case-sensitive, unter macOS und Windows meist nicht. Deshalb durchgehend kleinschreiben.
